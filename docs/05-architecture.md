## 6.2. Компоненты и зона ответственности

| Компонент | Ответственность | Что НЕ делает |
|---|---|---|
| **C1 Auth** | Регистрация, JWT, роли, возрастная категория, хранение согласий родителей | Не хранит контент и геоданные |
| **C2 Learning** | Модули курса, прогресс, автопроверка практики, выдача статуса и сертификата | Не выдаёт права — только сообщает Auth о завершении курса |
| **C3 Annotation** | Выдача заданий разметки, приём разметок, расчёт консенсуса, репутация разметчика | Не принимает решение о статусе участка (это ООПТ) |
| **C4 Events** | Акции, запись, вместимость, инструктаж, проверка допуска (курс + согласие) | Не создаёт акции сам — только по команде ООПТ/амбассадора |
| **C5 Reports** | Полевые отчёты, приём фото с EXIF-геометкой, очередь модерации | Не меняет статус участка напрямую — отправляет событие в C6 |
| **C6 Geo/Scoring** | Реестр участков, геометрия, статусы, история, пересчёт индекса внимания | Не работает с сырыми снимками — получает готовый сигнал от E |
| **E Конвейер ДЗЗ** | Приём, предобработка, нарезка, детекция изменений | Не принимает продуктовых решений — только поставляет сигнал S |

## 6.3. Данные ДЗЗ: источник и место в системе

Это ключевой пункт критерия, поэтому раскрываем отдельно.

| Этап | Что происходит | Технология | Результат |
|---|---|---|---|
| **F1 → E1. Источник** | Заявка на архивные/новые снимки через Геопортал Роскосмоса; для MVP — открытые Sentinel-2 и демо-набор | HTTP/S3-выгрузка, ручной ingest на MVP | Сцена (GeoTIFF) в объектном хранилище |
| **E2. Предобработка** | Проверка облачности, привязка, радиометрическая нормализация, обрезка по границам ООПТ | GDAL, rasterio (готовые библиотеки) | Нормализованный растр |
| **E3. Нарезка** | Перевод в Cloud Optimized GeoTIFF, генерация тайловой пирамиды | GDAL + TiTiler | XYZ-тайлы, отдаются клиенту напрямую из S3/CDN |
| **E4. Детекция изменений** | Сравнение разновременных сцен по одному участку: разность спектральных индексов, порог по площади и контрасту | rasterio + numpy (собственная логика, ~простая) | Кандидаты «зон внимания» + величина сигнала **S ∈ [0,1]** |
| **E4 → C6. Передача** | Кандидаты записываются как атрибут участка | Внутренний API / очередь | Обновлённый индекс внимания |
| **C6 → A2/A3. Потребление** | Волонтёр видит тайлы и получает задание разметки; ООПТ видит список приоритетов | REST + MapLibre GL | Сценарии S3, S4 |

**Принципиальное решение (обосновано критерием).**
На MVP **не строится ML-модель детекции мусора**. Критерий прямо допускает:
«Техническая обработка данных ДЗЗ не обязательна». Вместо этого:

- спутник даёт **грубый сигнал изменения** (дёшево, объяснимо, воспроизводимо);
- **точность обеспечивают люди** — консенсусная разметка волонтёров и
  подтверждение ООПТ;
- накопленные подтверждения формируют **размеченный датасет**, который на этапе 2
  становится обучающей выборкой для ML-модели.

Таким образом обучение волонтёров — это одновременно и образовательный продукт,
и способ получить разметку. Это и есть главная техническая ставка проекта.

**Резервирование источника (риск R-T1).** Если доступ к данным российской
группировки на пилоте не будет получен на приемлемых условиях (допущение C1),
система переключается на Sentinel-2 (10 м/пиксель, открытые) + аэросъёмка БПЛА
по ключевым участкам. Архитектура от этого не меняется: E1 абстрагирует источник.

## 6.4. Модель данных (основные сущности)

```
users ─────────────┬──< annotations >──── tiles ────┐
  id               │      id                 id     │
  role             │      user_id            scene_id
  birth_year       │      segment_id         bbox   │
  reputation       │      verdict            zoom   │
  oopt_id          │      created_at                │
                   │                                │
                   │                                ▼
                   │                          segments (PostGIS)
                   │                            id
                   ├──< enrollments >── events   geometry (LINESTRING/POLYGON)
                   │      user_id        id      oopt_id
                   │      event_id       segment_id   status
                   │      consent_id     starts_at    attention_index
                   │      attended       capacity     s_signal, c_consensus,
                   │                     status       t_recency, a_access
                   │                                  last_verified_at
                   ├──< field_reports >─────────────┘
                   │      id, user_id, event_id, segment_id
                   │      photo_before, photo_after (S3 keys)
                   │      geo_point, taken_at, volume_kg
                   │      moderation_status, moderated_by
                   │
                   ├──< course_progress >
                   │      user_id, module_id, completed_at, score
                   │
                   └──< consents >
                          id, minor_user_id, parent_contact,
                          signed_at, event_id, storage_ref
```

**Ключевые связи, обеспечивающие сквозные сценарии:**
- `annotations → segments` — разметка волонтёра влияет на `c_consensus` участка (S3).
- `segments.attention_index` — единственный источник сортировки в кабинете ООПТ (S4).
- `field_reports → segments.status` — наземный отчёт замыкает цикл (S6).
- `consents` — жёсткая блокировка допуска несовершеннолетних без согласия (S5).

## 6.5. Основные потоки данных

**Поток 1. Спутник → приоритет (асинхронный, раз в 2–4 недели)**
```
Геопортал/Sentinel → E1 ingest → E2 нормализация → E3 тайлы (S3)
                                        └→ E4 детекция → s_signal → segments
                                                              └→ пересчёт индекса
```

**Поток 2. Обучение → разметка → очередь ООПТ (сценарии S2, S3)**
```
Ученик → C2 курс → завершение → C1 повышает роль до «Наблюдатель»
    → C3 выдаёт задание (tile + пара сцен) → разметка
    → консенсус 3 независимых совпадений → c_consensus → C6 пересчёт индекса
    → участок попадает в очередь модерации ООПТ
```

**Поток 3. Акция → поле → верификация (сценарии S4, S5, S6)**
```
ООПТ подтверждает участок → C4 создаёт акцию → волонтёр записывается
    → C1 проверяет допуск (курс завершён + согласие для 14-17) → инструктаж
    → на месте: фото «до» (EXIF гео+время) → уборка → фото «после»
    → C5 отчёт → модерация ООПТ → segments.status = «чистый»
    → C6 пересчёт (t_recency обнуляется) → часы в ДОБРО.РФ → уведомление подписчикам
```

## 6.6. Технологический стек и обоснование

| Слой | Технология | Почему выбрана | Своё / готовое |
|---|---|---|---|
| Фронтенд | React + TypeScript, Vite | Массовая экспертиза, быстрый найм, PWA из коробки | Готовое |
| Карта | **MapLibre GL JS** | Open-source, без лицензионных ограничений (в отличие от Mapbox), работает с XYZ/COG | Готовое |
| Бэкенд | **Python 3.12 + FastAPI** | Один язык с геообработкой (rasterio/GDAL) — нет второго стека ради ДЗЗ | Готовое |
| БД | **PostgreSQL 16 + PostGIS** | Отраслевой стандарт для геоданных; пространственные индексы и запросы «из коробки» | Готовое |
| Объектное хранилище | S3-совместимое (MinIO / Yandex Object Storage) | Тайлы и фото не место в БД; прямая отдача клиенту | Готовое |
| Очереди | Celery + Redis | Конвейер ДЗЗ асинхронен и не должен блокировать API | Готовое |
| Геообработка | GDAL, rasterio, numpy | Зрелые библиотеки; не изобретаем обработку растров | Готовое |
| Тайл-сервер | TiTiler (COG) | Отдаёт тайлы динамически, не требует предгенерации всей пирамиды | Готовое |
| Авторизация | FastAPI + JWT, bcrypt | Требования простые; полноценный Keycloak избыточен для пилота | Готовое |
| **Индекс внимания** | Собственная логика (Python) | Ядро продукта, специфично для задачи | **Своё** |
| **Консенсус и репутация** | Собственная логика | Ядро доверия к волонтёрским данным | **Своё** |
| **Обучающий контур** | Собственная логика | Связка «курс → допуск» уникальна для проекта | **Своё** |
| Контейнеризация | Docker + Docker Compose | Требование воспроизводимости из ТЗ | Готовое |

**Правило выбора:** собственной разработкой закрываем только то, что составляет
суть продукта (приоритизация, доверие, связка обучения с допуском). Всё
остальное — зрелые готовые компоненты. Это снижает и стоимость, и риск.

## 6.7. Работа с персональными данными и аудитория 14+

Отдельный пункт критерия — раскрываем явно.

| Требование | Решение |
|---|---|
| **152-ФЗ, размещение данных** | Хостинг на территории РФ; персональные данные граждан РФ не покидают контур |
| **Минимизация ПДн** | Для базового участия достаточно имени и email; паспортные данные не собираются |
| **Несовершеннолетние 14–17** | Отдельная возрастная категория в профиле; офлайн-участие невозможно без электронного согласия законного представителя (жёсткая проверка в C4) |
| **Публичность профиля** | Профили 14–17 закрыты по умолчанию; в рейтингах — только имя и первая буква фамилии |
| **Геолокация несовершеннолетних** | Точные координаты фото не публикуются; в публичных слоях геометрия огрубляется до участка |
| **UGC-контент (фото)** | Обязательная модерация до публикации: автофильтр + проверка сотрудником ООПТ; кнопка жалобы |
| **Режим ООПТ** | Координаты уязвимых объектов (гнездовья, редкие виды) исключаются из публичного слоя; настраивается администратором территории |
| **Разграничение доступа** | RBAC; сотрудник ООПТ видит только свою территорию |
| **Аудит** | Неизменяемый лог модерационных решений — требование отчётности ООПТ |
| **Хранение согласий** | Отдельная таблица со ссылкой на файл; срок хранения ограничен и настраивается |

## 6.8. Развёртывание, масштабирование и эксплуатация

**Развёртывание (MVP и пилот)**
```
docker compose up  →  nginx · api · worker · postgres+postgis · redis · minio
```
Один хост, воспроизводимая сборка, соответствует требованию ТЗ об упаковке в
Docker. Порог входа для проверяющего эксперта — одна команда.

**Масштабирование (по мере роста)**

| Узкое место | Когда наступит | Решение |
|---|---|---|
| Отдача тайлов | Первым — при массовой разметке | Вынос тайлов на CDN; тайлы статичны и кэшируются |
| Хранение фото | ~10 тыс. отчётов | Объектное хранилище масштабируется независимо |
| Конвейер ДЗЗ | При росте числа территорий | Горизонтальное масштабирование Celery-воркеров |
| API | 10k+ MAU | Stateless-сервисы за балансировщиком; переход на Kubernetes |
| БД | Позже всего | Реплики на чтение; партиционирование `annotations` по времени |

Пиковая нагрузка предсказуема: она приходится на дни акций и на учебные занятия
в школах, а не распределена равномерно — это позволяет планировать ресурсы.

**Эксплуатация**
- Мониторинг: Prometheus + Grafana; алерты на сбой конвейера ДЗЗ.
- Логи: централизованный сбор, аудит модерации хранится отдельно.
- Резервное копирование: ежедневный дамп БД, версионирование бакета.
- Поддержка на пилоте: 1 инженер part-time; куратор для ООПТ (нетехническая поддержка).

## 6.9. Мультиязычность

Продукт поддерживает три языка интерфейса: **русский, английский, китайский**.

| Решение | Обоснование |
|---|---|
| Словарь «ключ → строка» вместо строк в коде | Добавление языка не требует изменений в логике приложения |
| Ключ + параметры вместо готовой строки в журнале событий | Журнал системы перерисовывается на новом языке целиком, включая уже записанные события |
| Локализуются и доменные сущности | Названия участков, статусы, роли, учебный курс — не только элементы UI |
| Автоматическая проверка согласованности | Скрипт сверяет совпадение набора ключей и плейсхолдеров `{...}` во всех языках |
| Выбор языка в `localStorage` | Сохраняется между сессиями; серверное хранение не требуется |

**Зачем это нужно проекту, а не просто «для галочки»:**

- **Русский** — основной рабочий язык проекта, ООПТ и волонтёров.
- **Английский** — публикация методики и данных; международные экспертные
  сообщества по ДЗЗ и citizen science (аналоги — Zooniverse, Marine Debris Tracker)
  работают на английском, и это канал для обмена практиками.
- **Китайский** — направление международного тиражирования модели: задача
  мониторинга береговых линий и охраняемых территорий с помощью ДЗЗ актуальна
  для стран с протяжённой береговой линией, а сам подход не привязан к
  российской специфике.

**Ограничение, которое мы признаём:** локализован интерфейс и учебный курс, но
не пользовательский контент (отчёты волонтёров, комментарии модерации) — он
остаётся на языке автора. Машинный перевод UGC на MVP не предусмотрен.

**Технические ограничения, которые мы признаём**

| Ограничение | Следствие | Что делаем |
|---|---|---|
| Облачность и периодичность съёмки | Данные обновляются раз в 2–4 недели, не в реальном времени | Управляем ожиданиями в UI: у каждого слоя видна дата съёмки |
| Разрешение снимка | Мелкий мусор со спутника не виден | Спутник даёт «зону внимания», а не диагноз; детализация — БПЛА и люди |
| Связь в поле | На ООПТ часто нет сети | Офлайн-режим PWA: отчёт сохраняется локально и отправляется при появлении связи |
| Качество волонтёрской разметки | Ошибки неизбежны | Консенсус 3 разметок + репутация + финальное подтверждение ООПТ |
| Сезонность | Зимой полевая активность падает | Зимой смещаем фокус на обучение и разметку (онлайн-контур продолжает работать) |
